# 联机写谱架构、连接方式与验收状态

## 目标与边界

联机写谱采用“房主权威、P2P 直连”的广义 C/S 模型，支持 2～8 个客户端协作。所有参与者运行同一个客户端和同一套协作代码，房主与访客在协作状态机中的结构差异只有 `isHost == true`。

- 房主和访客都在本地维护完整谱面，并根据同步后的本地谱面实时渲染。
- 客户端必须先设置默认 Creator；内部使用数值 `PeerId` 路由，界面统一展示房主广播的 Creator。
- 访客只向房主提交谱面操作；房主把本地与远端操作放入同一权威请求队列。
- 房主按接收顺序分配全房间唯一、连续递增的 `revision`，再广播已经提交的操作。
- 客户端只应用房主提交的谱面结果，不同步渲染数据和 ECS 实体编号；参与者视野与资源文件分别走轻量状态同步和独立资源同步流程。
- 新加入、缺少版本或落后到增量日志之外的客户端接收房主当前完整快照，再继续应用后续增量。
- 房主发布资源清单；访客按需从 DataChannel 接收本地缺失的谱面资源，并在写入缓存前校验内容。
- 当前不实现去中心化合并、房主迁移和离线编辑合并。

## 数据流

```text
访客本地编辑 ── 分类增量 EditRequest ──┐
                                        v
房主本地编辑 ──────────────────────> 房主权威请求队列
                                        │ 去重、排序、分配 revision
                                        v
                                 CommittedOperation
                                        │
                           ┌────────────┴────────────┐
                           v                         v
                     房主本地应用              P2P 广播给访客
                           │                         │
                           └────────────┬────────────┘
                                        v
                              各客户端本地谱面与渲染
```

`BeatmapSession` 在逻辑线程完成一次编辑后，只发布实际变化的数据类别。协作层把 `BeatMap` 规范化为以下四类增量之一或其组合：

- `objects`：Note、Hold、Flick、Polyline 及其引用、音效绑定和物件元数据。
- `timelines`：BPM、TimingEffect 和时间线元数据。
- `audio_samples`：音频样本时间、轨道、资源引用、音量及元数据。
- `metadata`：基础谱面信息和各格式扩展元数据。

负载使用 CBOR，并在超过阈值且压缩有效时使用 DEFLATE。外层带固定魔数、版本、压缩标志和未压缩长度；单条协作操作上限为 1 MiB，未压缩谱面文档上限为 64 MiB。分类增量避免每次编辑传输完整谱面，完整快照只用于房间初始化和恢复。

当前增量粒度是“变化类别的完整规范状态”。同一类别发生并发修改时，以房主队列后提交的状态为准。后续若需要合并同一类别内互不相关的并发编辑，可在不改动房主权威协议的前提下补充稳定对象 ID 和逐对象操作。

## 协议与恢复

WebSocket 信令只维护公开房间目录、房主准入、Creator、PeerId、SDP 和 ICE candidate；谱面与资源数据始终走可靠有序的 WebRTC DataChannel `mmm-collaboration-v2`。

协作二进制协议当前为版本 2，包含：

- `EditRequest`：客户端以 `(clientId, clientSequence)` 提交操作，房主据此去重。
- `CommittedOperation`：房主分配 `revision` 后广播的权威操作。
- `RevisionAck`：访客确认已经连续应用到的版本。
- `ResyncRequest`：访客检测到版本缺口后请求从指定版本补发。
- `StateSnapshot`：房主当前完整规范谱面及其对应版本。
- `ParticipantIdentity` / `ParticipantLeft`：`PeerId` 与 Creator 展示身份的增量变化。

房主保留有界操作日志。缺失版本仍在日志内时按顺序补发；日志已经裁剪时发送最新 `StateSnapshot`。重复请求、重复提交和旧快照均不会重复应用。

## 模块边界

全部联机实现都位于 `Modules/Network/Collaboration`，没有独立的顶层 Collaboration 模块。

- `CollaborationProtocol`：消息 DTO、二进制封包、协议版本、身份和大小校验。
- `CollaborationPeer`：统一房主/访客状态机、权威队列、版本、去重、日志和快照恢复。
- `ICollaborationTransport`：可靠有序字节通道抽象，不依赖谱面业务。
- `LoopbackTransport`：进程内确定性传输，用于丢包、重复包和 2～8 Peer 测试。
- `WebRtcTransport`：libdatachannel DataChannel、中心目录连接和临时 P2P 信令连接。
- `BeatmapDocumentCodec`：`BeatMap` 与压缩快照/分类增量之间的转换。
- `CollaborationRoom`：连接生命周期、Creator 身份、谱面观察者、应用回调和结构化日志。
- `CollaborationView` / `CollaborationLogWindow`：房间入口、连接信息、参与者和实时动态展示。

网络层不依赖 UI。UI 仅把房主提交后的谱面通过 `CmdReplaceBeatmapData` 放回固定的 `BeatmapSession` 命令队列，本地渲染流程无需感知网络。

## 如何连接

### 共同准备

1. 在“设置 → 软件”中填写“默认 Creator”。Creator 为空时不能开启或加入房间。
2. 只有房主需要先打开要共享的项目；访客可以在未打开项目的欢迎页直接连接。
3. 在“协作服务器”设置中填写服务器域名和端口；公网生产入口默认使用 `xiang233.top:443` 与 TLS/WSS。
4. 访客获准连接后会用房主完整快照创建本地协作会话，并按资源清单拉取本机缺失资源。

### 房主

1. 打开左侧双人图标的“协作”页，确认协作服务器配置已经连接。
2. 填写公开房间名并点击“开启协作房间”；房间会自动出现在在线目录，无需另发房间码。
3. 访客申请加入后，在待处理列表中批准或拒绝；只有批准后才会建立双方 P2P 通道。
4. 房主可把其他参与者移出房间；房主退出或服务重启会结束本次房间，不会迁移房主。

### 访客

1. 直接打开“协作”页，无需预先打开项目。
2. 刷新在线房间目录，在目标房间行内点击“加入此房间”。
3. 等待房主批准；连接成功后自动同步谱面、资源和参与者状态。
4. 参与者列表会展示所有 Creator，并提供跟随与房主移出操作；“协作日志”窗口实时显示准入、连接、同步、提交版本、断线和错误。

公网连接仍然是 P2P 优先：ICE 先尝试本机候选和 STUN 发现的公网候选，只有 NAT 或防火墙阻止直连时才回退 TURN/UDP relay。无论选中哪种 ICE 路径，业务层始终使用同一条 DataChannel；中心信令服务只负责目录、准入和建连消息。TURN 兜底会消耗服务器带宽，但正常打洞成功的参与者不会经服务器转发谱面数据。

### 本机启动多个客户端

```bash
scripts/run-local-collaboration.sh \
  build/bin/MusicMapMaker-Next \
  /path/to/project \
  8
```

脚本为每个进程设置独立的 `MMM_CONFIG_ROOT` 和唯一的 `MMM_CREATOR`，避免多个客户端争用配置。只有第一个客户端自动打开项目并作为房主，其余客户端停留在欢迎页，使用 `127.0.0.1`、显示端口和房间码连接。客户端总数可指定为 2～8。

手动覆盖 Creator 时必须把变量传入应用进程。bash/zsh 可使用
`MMM_CREATOR=Client1 ./MusicMapMaker-Next`；fish 可使用
`env MMM_CREATOR=Client1 ./MusicMapMaker-Next`，或先执行
`set -gx MMM_CREATOR Client1`。仅执行 `set MMM_CREATOR Client1` 时，fish
自身的 `echo` 可以看到该变量，但子进程无法读取。

## 第一阶段验收标准

`CollaborationPeerTest` 在无图形界面下创建 1 个房主和 7 个访客，验证并发请求产生唯一连续版本、最终模型一致、重复消息不重复应用、缺失增量可补发、日志裁剪后可回退快照。`CollaborationRoomTest` 使用真实 WebRTC 信令和 DataChannel 创建相同规模的房间，验证 Creator 身份、初始谱面、访客编辑、房主编辑和断开流程。两套测试共用同一 `CollaborationPeer`，传输层不改变权威状态机。
