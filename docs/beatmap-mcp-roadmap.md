# 谱面编辑 MCP 服务搭建路线

**状态：设计提案。** 盘点基线为主仓 `2d23edb3`。目标使用场景是作者选定当前谱面和一个乐句，让模型听这一段音乐，阅读前后段的写法，提出可以比较的编排，最后由同一编辑器执行、试听和撤销。自动写谱也走相同的提案与提交路径，作者可以预先授权指定谱面、区间和操作类型。

## 二、让模型听、读和设计

一次编排跨越三类数据。**证据**回答“哪一拍听到或读到了什么”，**解释**回答“作者可能在强调什么”，**候选编排**回答“具体要放哪些物件”。三类记录分开保存。每条解释关联证据、分析方法和适用区间；每个候选注明采纳了哪些解释。作者可以拒绝“这次转向代表旋律上行”，同时保留检测到的起音和原谱。

| 能力 | 输入与产出 | 校验与降级 |
| --- | --- | --- |
| 分段听音 | 输入工程音频资源、拍区间及两侧上下文。解码器输出限长片段，携带 MIME、采样率、源帧范围、谱面偏移、节奏图版本。具备音频输入的客户端把片段交给模型，模型按时间标出重拍、起音、延音、音色切换、乐句边界及听感依据。 | 客户端接收音频和模型实际可听是两项能力；接入验收要实测两者。只有文本输入时返回节拍、瞬态、能量等特征，并标识依据。已有[波形分析](../Modules/Game/UI/src/ui/imgui/audio/WaveformAnalysis.cpp)和[BPM 检测](../Modules/Game/UI/src/ui/imgui/menu/actions/tools/BpmAutoDetector.cpp)可作为提取入口。 |
| 音色与声部分解 | 工程已有独立音轨时直接独听。只有混音时，由可选分离器生成鼓、低音、人声等估计声部；每轨保留相同源时间轴、模型版本和内容摘要。允许模型分别听声部，再回听同一拍的混音。 | 声部是估计值，串音、弱瞬态和分离误差随结果返回。不同声部的同一瞬态按时间聚类并保留来源，避免生成双份音符。缺少分离器时仍可用混音完成提案。 |
| 阅读 Note 排列 | 对参考段按拍序提取同时起音组、轨道序列、间隔、长条占轨、滑向与密度。按相对拍和相对轨归一化，找重复、移位、镜像、变奏；输出原对象 ID 与反例。 | 将“每半拍交替两轨”这类可重算描述与“左右手呼应”这类解释分栏。手法推测带键数、指法假设和置信说明；跨段 Hold 纳入占轨。 |
| 规划 Polyline 表意 | 模型先描述乐句手势，例如“延音保持位置，音色切换时折返”；再给出有拍点、目标轨和音乐依据的锚点。路径编译器产出明确的 Hold/Flick 序列及各次转向，返回时间–轨道图和试听位置。 | 检查起止轨、轨道边界、子物件交替、Hold 与相邻 Flick 时间严格衔接、父物件取首子物件位置。模型给出备选走向；交叉占轨、转折频率、目标格式损失随预览显示。[Polyline 不变量](../Modules/MMM/include/mmm/note/Polyline.h) |
| 段落规划与比较 | 输入作者指定的难度、主次声部、留白和参考段。先产出按乐句排列的意图表，再生成若干覆盖相同区间的候选，报告密度曲线、节奏覆盖、并键数、占轨冲突和引用动机。 | 结构校验决定候选能否提交；音乐表现交由作者在相同混音、速度与上下文下 A/B 试听。模型解释可回溯，主观评分不充当正确答案。 |

**贯穿验收的案例。** 作者选中八拍副歌，要求“前四拍延续主歌的交替，后四拍用折线跟随人声尾音”。读取相邻主歌的排列与副歌的混音，比较鼓点和人声起音。候选 A 保留鼓重拍，尾音用一次折返；B 减少伴奏落键，折线延长到下一次换气。两案返回相同时间窗、实际对象差异、对应试听片段及可读路径。作者只采纳 B 的后四拍时，重新预览该子集并检查跨段长条。一次提交形成一条撤销记录。该案例既验证听音和读谱，也能暴露时间偏移、误删前半段和路径断裂。

### 优先前置功能：音轨分离与试听

工程已有独立音轨时直接读取。只有立体声混音时，使用预训练音乐源分离模型估计人声和乐器声部。第一版以人声、鼓、贝斯、其他四轨建立基准，允许任意组合。公开评测支持把 **SCNet / SCNet-large 放到首轮验证的首位**。模型返回各权重支持的类别，“其他”可能同时含有多种乐器。

| 场景 | 优先验证的模型 | 选型依据 |
| --- | --- | --- |
| 四轨通用分离 | 官方 SCNet 与 SCNet-large，Demucs `htdemucs` 作为对照 | 在同一项公开评测的 MUSDB18-HQ 测试上，官方 SCNet Small 与 Large 的平均 SDR 分别为 9.03 和 9.70 dB。原论文报告标准 SCNet 的 CPU 推理耗时约为其 HT Demucs 对照的 48%。作者确认官方发布的两种权重采用 MIT 许可证，可按要求署名分发。[评测表 3](https://reference-global.com/article/10.5334/tismir.366?tab=figures-and-tables) · [SCNet 论文](https://arxiv.org/abs/2401.13276) · [官方权重授权确认](https://github.com/starrytong/SCNet/issues/35) |
| 更干净的人声 | 人声专用 BS-RoFormer 或 Mel-Band RoFormer | 在 Multisong MVSep 的人声评测中，多个特定 RoFormer 权重超过 SCNet Large。记录具体权重与推理参数，单独核对分发条件。[评测表 1 与表 9](https://reference-global.com/article/10.5334/tismir.366?tab=figures-and-tables) |
| 吉他与钢琴 | 专用 RoFormer 权重或 Banquet，`htdemucs_6s` 作为对照 | 评测中的吉他 BS-RoFormer 为 7.12 dB，对照为 5.24 dB。钢琴 Mel-Band RoFormer 为 5.71 dB，对照为 2.23 dB。Banquet 论文在 MoisesDB 上也报告吉他和钢琴优于六轨 HT Demucs，并需要评估查询音频的准备成本。[评测表 4 与表 5](https://reference-global.com/article/10.5334/tismir.366?tab=figures-and-tables) · [Banquet 论文](https://arxiv.org/abs/2406.18747) |
| 底鼓、军鼓、踩镲 | 鼓组专用 DrumSep，或具备相应输出的 SCNet XL / Mel-Band RoFormer 权重 | 按需实测鼓件拆分。评测中各模型的强项随鼓件变化，尤其要检查踩镲串音和瞬态保留。[评测表 8](https://reference-global.com/article/10.5334/tismir.366?tab=figures-and-tables) · [可用权重目录](https://github.com/ZFTurbo/Music-Source-Separation-Training/blob/main/docs/pretrained_models.md) |

#### 按声部分别选模型

每个目标声部独立选择权重，例如人声用 KimberleyJSN 的 Mel-Band RoFormer，贝斯用官方 SCNet-large 的 bass 输出，鼓组用鼓分离评测中胜出的权重。默认让每个模型读取同一份原始混音，只保留指定输出。模型如果必须同时算出多个通道，仍可复用同一次推理，按配置决定每条声部是否采用。鼓件等细分允许单独评估“原曲直出”和“以已分离鼓组为输入”，作业清单记录实际输入以及上游版本，避免级联误差被当成独立证据。

- **选择依据。** 每个声部维护一份候选和回退顺序。用同一批有参考分轨的写谱曲目逐轨比较，登记权重、设备和推理参数。鼓优先看瞬态定位与弱起音召回，人声和钢琴看延音、稀疏段串音及音头保留，贝斯看低频音头与底鼓混淆。SDR、耗时和峰值内存一并记录。默认选择该声部在项目样本上实测通过、且符合分发条件的权重。
- **权重许可。** 已确认官方 SCNet 与 SCNet-large 权重为 MIT。KimberleyJSN 人声 Mel-Band RoFormer 的权重仓库标 MIT。Becruily 吉他权重的作者声明一般限非商业使用。ViperX、其他社区钢琴、鼓件或 SCNet XL 权重按具体文件核对，未确认的保留为评测候选。登记权重来源、版本、SHA-256、许可证据和允许的分发方式，分别核对代码、运行库和权重。[SCNet 作者确认](https://github.com/starrytong/SCNet/issues/35) · [KimberleyJSN 人声模型](https://huggingface.co/KimberleyJSN/melbandroformer) · [Becruily 吉他权重授权答复](https://huggingface.co/becruily/mel-band-roformer-guitar/discussions/9)
- **试听与混音。** 每条独立提取轨按原曲帧坐标对齐、保留增益，可单独听，也可与其他声部组合试听。不同模型可能重复提取同一瞬态，也可能遗漏同一成分。全开时可通过 A/B 对照原曲。需要剩余轨时，可单独评估原曲减去已选声部的差分，标识为“残差”并披露伪影。鼓组与军鼓等父子轨在同一混音中互斥，各自仍可独立读取。
- **缓存与 MCP。** 只运行当前请求的声部，按源内容、目标声部、权重、参数及上游输入版本缓存。各声部独立发布进度与结果。MCP 清单返回轨道角色、分析轨或可混音组、来源和模型版本；取样继续用轨道 ID 与原曲时间范围。同一声部换模型时生成新产物 ID，已引用旧版本的分析保持可复查。

**运行与数据。** 编辑器启动可选的本地工作进程执行分离，显示进度，允许取消。第一轮以 CPU 能完成为准，显卡加速按三平台实测纳入支持范围。主程序按需加载产物，无须加载 Python 或模型运行库。先分离完整曲目并缓存，再按时间切片，给连续试听和跨片段拼接提供统一源帧坐标。缓存以来源内容、预处理参数、模型与权重版本为键。每组声部附清单，记录可用声部 ID、来源资源、采样率、帧数和原音频起点。执行前核对代码、权重及运行库的分发条件。作业失败或取消时保留原曲及上次成功结果。单轨通过完整性及对齐检查后发布，整组替换则在全部成员检查通过后发布。

**编辑器试听。** 针对原曲和分离结果提供 A/B 切换。分离结果的每轨独立启停，支持独听、全开和全关。任意组合共享播放头、定位、循环区间和速度设置。全关时声部总线静音，播放头照常推进。切换时用短增益过渡，原曲与分轨组合互斥以避免叠加。第一版将这些控制保存为试听状态，谱面的 BGM、键音绑定及导出遵循现有工程设置。现有播放控制已处理键音与草稿/BGM 的静音命令，可从同一播放入口接入独立试听总线。[现有播放控制](../Modules/Game/Logic/include/logic/session/PlaybackController.h)

**MCP 复用。** `audio_list_tracks` 返回当前授权资源的原曲、原生分轨和已生成声部，附稳定 ID、类别、来源及可用区间。`audio_excerpt` 接收一个或多个 ID 和区间，明确请求“逐轨返回”或“按选择混合”。时间输入支持秒或拍，拍区间需绑定节奏图修订。每个结果都附原音频帧区间与谱面时钟映射。客户端可独听第 32～40 拍的人声，也可在同一请求获取鼓和贝斯的独立片段进行对照。编辑器试听与 MCP 切片共用轨道清单和取样逻辑，工具调用不依赖 UI 的启停状态。

**落地顺序。** 先用原始音频和已知对齐的人工分轨实现播放、切片与列表契约，再接模型验证来源对齐和分离质量。这样在模型选型完成前，编辑器和 MCP 已可使用真实多轨素材。第一版回归覆盖任意轨道组合、全关、播放中启停、seek/循环、首尾越界处理、试听与 MCP 取样的一致性，以及分离失败和缓存失效。用有参考分轨的样本测相对延迟和串音，并记录低、中、高配置设备的耗时与峰值内存。模型质量决定某个声部可作何种分析依据。

#### 编辑器内分离与混音

在音轨列表中打开项目主音轨的控制器，展开“声部分离”。模型目录列出可部署模型、擅长的声部及当前绑定状态。选择某一行的“部署”并指定父目录，MMM 会下载官方权重、创建该模型自己的虚拟环境、安装依赖并保存绑定。首次部署需要本机可用的 Python 3.11 或 3.12，分离还需要 FFmpeg。也可通过“绑定已有”复用完整的模型目录或其 `env` 子目录。各模型的绑定在下次启动时恢复。分离直接以该控制器对应的主音轨为输入，结果自动进入同一区域的混音台，可逐轨调节推子、启停和独听。音效轨控制器没有此入口。

目录目前提供 HTDemucs 四轨与六轨，前者覆盖通用人声和节奏组，后者增加吉他与实验性的钢琴声部。已有 MSST 模型仍可通过“高级 · 自定义模型”导入并使用其独立配置。

外部模型包是 JSON 描述文件，引用发布者提供的配置和权重。相对路径以 JSON 所在目录为基准。`tracks` 的键是编辑器显示的声部 ID，`target` 是推理后端实际写出的声部名。单模型可用一个包列出多个输出，组合包也可指定不同模型各取一轨。以下文件名是本地示例，需要与实际下载的权重匹配。[MSST 推理入口](https://github.com/ZFTurbo/Music-Source-Separation-Training#how-to-inference)

```json
{
  "version": 1,
  "tracks": {
    "vocals": {
      "model": "mel_band_roformer",
      "target": "vocals",
      "config": "models/vocals.yaml",
      "weights": "models/vocals.ckpt"
    },
    "bass": {
```

## 三、服务边界与操作目录

**首选接入方式为编辑器内置 Streamable HTTP 端点。** 作者在编辑器中启用本机 MCP，复制当前实例展示的 `http://127.0.0.1:<端口>/mcp` 到支持 HTTP 的 MCP 客户端，并单独配置访问凭据。客户端向该 URL 发送 MCP JSON-RPC 请求。端口可配置，首次成功绑定后记住；多实例或端口占用时显式展示新地址，由作者选择目标实例。服务仅绑定回环地址，校验来访 Origin（如有）和实例凭据，关闭服务即停止接入。

请求路径为 **本机 MCP 客户端 → 编辑器 HTTP 接入层 → 谱面查询或编辑服务**。接入层在后台处理连接、协议和 DTO；查询读取发布的快照，写入排入逻辑线程，由编辑器维护当前未保存的修改和撤销历史。关闭客户端后仍可继续手工编辑。云端模型由本机客户端代调时也沿用此路径；只有 MCP 客户端自身运行在远端时才需要另行设计可达端点。

MCP 定义 stdio 和 Streamable HTTP 两种标准传输。stdio 适合客户端按命令启动子进程，本项目的编辑器通常已经由作者打开；直接连接实例可省去桥接进程及平台专用 IPC。S0 记录目标客户端的 URL、认证头和媒体支持情况；遇到仅支持 stdio 的实际客户端时，再评估复用同一 HTTP 端点的薄适配器。协议版本与领域 schema 独立登记。[MCP 传输规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports) · [Filesystem 参考实现](https://github.com/modelcontextprotocol/servers/blob/main/src/filesystem/index.ts) · [Playwright MCP 独立服务示例](https://github.com/microsoft/playwright-mcp#standalone-mcp-server)

| 提议工具 | 主要输入 → 输出 | 执行归属 |
| --- | --- | --- |
| `chart_context` | 会话 → 谱面身份、修订、格式、轨数、权限、可用操作及限制 | 编辑器发布只读上下文 |
| `chart_query` | 区间、类型、字段、游标 → 有版本的对象、事件、注记或统计页 | 会话快照；跨页沿用同一版本 |
| `audio_list_tracks` / `audio_excerpt` | 资源 → 声部清单。所选声部、区间与混音选项 → 限长音频及精确时间映射 | 共用编辑器的轨道清单和切片服务 |
| `analysis_start` / `job_get` / `job_cancel` | 分析类型、输入引用、参数 → 任务状态、证据或产物引用 | 后台分析；分离、特征、排列分析分别声明支持度 |
| `edit_preview` | 基线、目标、带类型的操作列表 → 计划 ID、差异、诊断、预览资源 | 领域规划器；适用于人机共同编辑与自动写谱 |
| `edit_commit` / `edit_result` | 计划 ID、请求键 → 结果、新修订、对象映射及历史条目 | 逻辑线程；支持断线查询 |
| `chart_export` | 已授权目标、格式、选项、基线 → 预检或产物任务 | 工程服务；单独授权文件写入 |

工具数量可以保持稳定。每个操作族单独发布版本化 JSON Schema，以带判别字段的联合类型表达参数，例如 `note.create`、`hold.resize`、`selection.mirror`、`timing.insert`、`polyline.replace_path`。查询目录返回当前格式、版本和权限允许的子集。schema 中登记单位、必填字段、批量上限、失败码、撤销语义与样例；从同一注册表生成工具描述、校验与覆盖清单。只读资源可承载长结果，核心工具保留分页读取路径。SDK 与实现语言在 S0 按客户端互通、包体积和三平台可分发性选定。[MCP 工具契约参考](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

## 四、编辑契约与一致性

下面是一段四轨谱面的建议 wire payload。拍号坐标以谱面约定的拍零点为原点，拍数用约分后的有理数，玩家轨道从 0 开始。区间统一为左闭右开；查询支持“在区间内起音”和“与区间相交”两种模式。绝对时间另设显式单位，解析拍坐标时绑定同一节奏图；遇到停顿边界须返回所用边界侧或要求消歧。

```json
{
  "schemaVersion": 1,
  "chartId": "chart-1",
  "generation": "open-3",
  "baseRevision": 42,
  "operations": [
    {"op": "note.create", "ref": "accent", "beat": [32, 1], "lane": 0},
    {"op": "hold.create", "ref": "tail", "beat": [65, 2], "endBeat": [34, 1], "lane": 2}
  ]
}
```

1. **标识与作用域。** `chartId + generation` 区分同文件的不同打开实例。检查已有[物件身份](../Modules/Game/Logic/src/logic/session/NoteIdentity.cpp)在复制、撤销、重载和格式往返时的行为；缺少持久身份的类型先使用会话内稳定句柄。计划内的临时引用在成功时映射为实际 ID。只读游标、计划和媒体引用均绑定版本和有效期。
2. **预览。** 在不可变基线上解析选区，按顺序求值操作并检查最终状态。返回增删改数量、受影响区间、示例差异、完整分页结果及逐操作诊断。按目标格式区分非法数据、可编辑但导出有损、审美提示。相同输入应生成相同语义差异。
3. **提交。** UI、插件与外部写入共享变更通知；应覆盖直接修改元数据等入口。逻辑线程在应用点复核实例、修订和授权，提交预览时已冻结的差异。实施前验证批量历史能容纳对象、时间线和子物件，任一失败均保持原状态；整批成功后只发布一次修订和一次撤销记录。协作开启时最终成功须等房主确认。[会话分发](../Modules/Game/Logic/src/logic/session/BeatmapSession_Commands.cpp)
4. **重试与恢复。** 编辑结果区分排队、已应用、冲突、失败。请求键绑定调用者、谱面实例和请求摘要；同键同内容返回原结果，同键不同内容报错。冲突返回当前修订与需重读区间，客户端重新预览。HTTP 连接中断后按请求键查询；编辑器重启时明确返回旧实例已结束及结果是否可判定，禁止自动重放未知结果。
5. **边界与预算。** 背景线程做音频解码、分离、序列化和预览准备；逻辑线程独占短时提交。按缓存键复用音频内容摘要、解码参数、分离器版本和片段范围；拍坐标派生结果另绑定节奏图修订。限制作业数、音频字节数、响应大小与单批对象数。上限由 S1/S4 基准测定并随能力查询返回。
6. **授权。** 分开授权读谱、向模型提供音频片段、区间编辑、文件导出；外部分析供应商获得音频需要作者选择。自动模式可限定轨道、时间范围和对象数。编辑器记录计划摘要、修订和调用结果，允许作者随时撤销授权。远程 HTTP、多用户托管属于后续部署决策。

## 五、实施顺序与验收门槛

| 阶段 | 交付物与依赖 | 合入前可复验的结果 |
| --- | --- | --- |
| S0 领域盘点与协议冻结 | 建立“现有入口 → 作者意图 → 领域类型 → 可用格式 → 测试”清单；登记 92 个命令以及 UI/文件入口的覆盖、合并或保留理由。冻结 v1 坐标、身份、修订、权限、错误及样例。 | 用同一组 schema 验证合法与非法样例；确认目标客户端支持的协议版本、音频内容、资源读取方式；记录兼容矩阵。 |
| S1 本机只读 | 完成回环 HTTP 端点、实例选择、快照、分页和能力查询。先覆盖对象、时间线、轨道、音频引用。 | 用支持 URL 的客户端完成工具发现与查询；覆盖端口占用、无效凭据和非法 Origin；两个编辑器实例互不串谱；能读到未保存的编辑；关闭、切谱或翻页期间编辑有确定结果。在大谱播放中比较开启前后帧时间、逻辑更新与峰值内存。 |
| 音频前置任务 | 可与 S1/S2 并行。先完成多轨试听、轨道身份和取样，再用本地模型生成四类声部。 | 来自编辑器与 MCP 的相同轨道组合和区间应对齐，模型关闭时仍可试听原曲和原生音轨。 |
| S2 可撤销的最小写入 | Note/Hold 增改删、预览与原子提交、请求去重。支持人工采纳与有范围的自动提交。 | 同一候选提交两次只生成一批物件；并发手改造成冲突；中途失败无残留。撤销/重做后逐字段比较、保存并重开。 |

| S4 音乐理解与辅助创作 | 基于音频前置任务的声部读取与节拍特征，结合 S2/S3 完成从意图到候选的闭环。 | 使用有权使用的已知分轨、已知起音及人工标注谱段。测片段首尾帧偏差、声部对齐、起音偏差、排列检索及折线合法率；记录运行耗时和硬件。用第二节副歌案例分别验收可听音、纯文本与无分离器路径，作者试听比较。 |

首批评审可以直接以三个产物为准：**领域操作注册表、可往返的谱段样例、两个候选的差异与试听记录**。它们分别检验接口能否演进、编排是否忠实落地，以及模型是否真正帮助作者做决定。
